# Combat Lab — separate opt-in test build

This is a **test build**, not a finished Crystal Aura or AutoTotem. The normal Apollon build omits the Lab unless the build environment contains `ECLIENT_COMBAT_LAB=1`; `.github/workflows/combat-lab.yml` does that and creates `eclient-combat-lab-arm64`. Use the pinned 1.21.111 ARM64 APK and back up worlds before changing installations: debug signing keys are regenerated.

A separate **Console** category in the left-side category list shows the latest 100 events in memory, including hook installation, placement attempts/returns, transfer calls and occasional crystal-attack events. Scroll its event area, use Follow latest to track new entries, or Clear console. It contains no Downloads file and is reset on process restart. Transfer observation starts enabled; stop/start it from Combat Lab. Calls and return values are not confirmations. Screenshots can show world coordinates from placement tests.

The Console page also has the placement controls, so they are accessible without scrolling through Combat Lab. Choose a method and direction, tap **Arm placement test (30s)**, leave the menu and manually use a crystal on an obsidian block with a second obsidian block in the chosen direction. Then reopen Console for events and check both blocks; the extra call could consume the held stack before the manual call. If it expires without a hook event, the game path was not intercepted; if the call is recorded, check whether a crystal appeared on the adjacent block. The GameMode method now shifts the absolute hit point with the candidate position. The EndCrystalItem method hooks the item class slot 123 and calls that same item routine for the adjacent position when it is reached, using live call arguments; it may not run on the client, might only affect client state, or could crash. Check after leaving and re-entering the world. The GameMode method uses whatever item was held, not item identification.

Combat > Combat Lab contains:

- **Arm one crystal attack (10s):** on the next eligible game tick, find the nearest existing actor with previously observed crystal type ID 71 within four blocks and call the existing Apollon attack wrapper once. No actor is retained across ticks. It cancels on panic/menu/death and expires after 10 seconds. `Attack attempted` means the function was called, not that a crystal broke. The one-shot button itself does not place crystals or automatically target players.
- **Continuous crystal break:** repeatedly attacks the nearest crystal within four blocks, at most twice per second. It has no damage calculation, placement targeting or target-player selection.
- **Adjacent placement attempt:** arm the test, hold a crystal and manually use it on an obsidian block within 30 seconds. By default, the hook calls the same game function first with a copied block position shifted one block in the selected direction, then forwards the manual use. The previous after-manual order is selectable for comparison. All other arguments are the live arguments from your manual use. A neighboring obsidian block is needed. GameMode also shifts the copied hit location; EndCrystalItem slot 123 uses the observed item routine and its inferred by-value position ABI. These are guessed placement ABIs; it can place any held item and the call/return value is not proof of placement. It is assisted rather than autonomous.
- **Extra transfer call:** arm it, then manually move a totem into your offhand. When the candidate transfer hook sees its next valid call, it actively invokes the original native transfer once extra with those live arguments and then forwards the game call as normal. This is a duplicate of the manual transaction, not autonomous totem selection, and may cause desynchronization, item loss or crashes. The status only means the extra function was called. It is an experiment, not AutoTotem.
- **Transfer observation:** at startup this test build installs a passive hook on the matched `ContainerTransferClient` slot 3 target `0xcdc921c`, but only if the target's first 16 bytes equal the verified pinned-library prologue. When observation is started, the page counts calls and whether the first two arguments are non-null; logcat tag `EClientCombatLab` additionally logs up to 25 events and whether the third argument is nonzero. It does not read inventory bytes, retain raw pointers, call the function itself, equip a totem or prove an event was accepted. The hook is installed even while observation is stopped and cannot be uninstalled without restarting the game.

The transfer function is **inferred** from targeted Ghidra output as `void(self, input, third)`; its ABI, thread context and side effects are not validated. A hook can interfere with normal play, corrupt state or crash even when its prologue matches. The extra-transfer test does invoke an additional native transfer but does not select a totem automatically; item identity, ownership and request semantics are unknown. The transfer observer tests whether manual operations reach the candidate, not whether AutoTotem is complete. Test only in a backed-up disposable local world, not a valuable world or multiplayer server. A successful call/event is not proof of server acceptance; compare the actual inventory/crystal on screen. The console is process-local, no Downloads log is created, and a crash can clear it. Logcat can be collected separately if available.
